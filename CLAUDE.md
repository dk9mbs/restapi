# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A metadata-driven REST API framework (Flask + flask-restx + MySQL/PyMySQL). Almost nothing about the data model is hardcoded in Python: tables, fields, views, permissions, formatters and lookups are all rows in `api_table*` / `api_group_permission` / `api_table_view` tables, read at request time via `core/meta.py`. Application-specific behavior (bank imports, IoT/MQTT devices, APRS, ham-radio ADIF logging, etc.) lives entirely in `plugins/`, which are ordinary Python modules registered in the `api_event_handler` DB table and invoked by publisher/trigger name — there is no static registry of plugins in code.

## Running the app

```bash
. ./init.sh          # creates/activates venv at venv/restapi, sets PYTHONPATH (repo root + plugins/ + formatter/ + configured plugin root)
python restapi.py    # dev server, reads config.py CONFIG['default']
```

`config.py` (gitignored local secrets, copy from `config.skelet`) holds the MySQL connection, server host/port, plugin root, and `ui.wwwroot`. Production runs under uwsgi/systemd units generated by `install.sh` (`restapi.<instance>.service`, `restapi-timer.<instance>.service`, `restapi-msg.<instance>.service` for `timerservice.py` / `msgservice.py`).

`install.sh` bootstraps a full instance: creates the DB, loads `install/db/install.sql` + `basedata.sql`, builds the metadata cache via `tools/metadata.py`, then runs `install/db/post_metacache.sql`.

## Tests

Tests are `unittest`-based and require a **live MySQL database** — each test's `setUp` calls `AppInfo.init(...)` and logs in as `root`/`password` against the DB configured in `config.py`. There is no mocking layer.

```bash
. ./init.sh
python -m unittest discover -v -s test          # all tests, from repo root
python -m unittest test.test_database_crud -v   # single module
python -m unittest test.test_database_crud.TestDatabaseCrud.test_insert -v  # single test
```

`test/integrationtest.sh` additionally drops a throwaway plugin module into `/tmp` before running the suite — used for plugin-execution tests that `importlib.import_module` a plugin by name.

## Architecture

### Request lifecycle
`restapi.py` builds the Flask app via `AppInfo.init()` (in `core/appinfo.py`, which owns the Flask app, the three `flask_restx.Api` blueprints — `api`, `ui`, `portal` — and the raw MySQL connection pool), then imports each `api.*`/`ui.*` endpoint module and wires it to a URL with `AppInfo.get_api().add_resource(...)`. Endpoint modules follow one pattern: a `flask_restx.Resource` subclass with `get`/`post`/`put`/`delete`, and a module-level `get_endpoint()` returning the class.

`before_request` in `restapi.py` resolves auth for every request (session cookie → `restapi-username`/`restapi-password` headers → `username`/`password` headers or query args → `apikey` → anonymous guest login with `auto_logoff`), builds a `Context` via `AppInfo.create_context(session_id)`, and stores it on `g.context`. `teardown_request` commits/closes or logs off that context depending on `auto_logoff`.

`core/context.py`'s `Context` wraps one DB connection plus request args, session values and user info; it's threaded through nearly every core/services call instead of using Flask globals directly (so plugin code, which runs in worker threads, gets its own `Context`).

### Two parallel SQL-building paths, one executor
- **FetchXML** (`core/fetchxmlparser.py`, `FetchXmlParser`) — the original, XML-based mini-DSL (`<restapi type="select|insert|update|delete"><table.../><filter>...`) used throughout the `api.data.*` endpoints and by `build_fetchxml_by_alias` (`services/fetchxml.py`).
- **FetchSQL** (`core/fetchsqlparser.py`, `FetchSqlParser`) — newer, parses real SQL text via `sqlglot` and decomposes it into the *same* internal representation `FetchXmlParser` uses, so all of `FetchXmlParser`'s `get_select()/get_insert()/get_update()/get_delete()` rendering and validation (allowed identifiers/operators/functions, join-kind whitelist) is inherited for free. Every table/alias is re-validated against `api_table` metadata.
- **ORM** (`services/orm/`) — a small Django-esque layer: `BaseModel`/`BaseManager`/`Field` subclasses (`StringField`, `IntField`, `BoolField`, `DateTimeField`, `DefaultField`) plus `Q`/`F`/`O` expression helpers (`f.py`, `expression.py`). `BaseManager.select()/insert()/update()` build a plain dict describing the query and hand it to `core/ormparser.py`'s `OrmParser` (also a `BaseParser` subclass) — a third producer of the same internal shape. Model classes are handwritten per table (see `shared/model.py`) and bind `Field` descriptors to columns via `MetaModel.__new__`.

All three parsers (`FetchXmlParser`, `FetchSqlParser`, `OrmParser`) ultimately produce `(sql, params)` consumed through `services/database.py`'s `DatabaseServices.exec(parser, context, ...)`, which enforces table-level permissions (`core/permission.py::Permission.validate`, checked per table against `api_group_permission`) before running the statement and wrapping the cursor in a `Recordset` (`core/database.py`) for pagination/formatting.

### Metadata
`core/meta.py` reads table/field/view metadata straight from `api_table`, `api_table_field`, `api_table_field_type`, `api_table_view` (joined with control + lookup-function metadata) on every request — there is no in-process cache beyond what `tools/metadata.py`/`core/meta_builder.py` precompute into those tables at install time. Field `control_config` JSON is merged from the field-type default and any per-field override.

### Plugin/event system
`core/plugin.py`'s `Plugin(context, publisher, trigger)` looks up enabled rows in `api_event_handler` matching a `(publisher, trigger)` pair, `importlib.import_module`s each `plugin_module_name`, and calls its `execute(context, plugin_context, params)` for the `type` phase requested (`'before'`/`'after'`). Plugins run either synchronously (`SyncWrapper`) or as a background thread with its own system-login `Context` (`AsyncWrapper`), and optionally expose a `config()` function (e.g. `{"raise_exception": False}`) read via the `Config` helper. Every plugin's run is journaled in `api_process_log`/`api_event_handler.status_id` by `ProcessTools`. Table-change events, app-start (`$app_start`), timers, and user actions (`/v1.0/action/<action>`, see `api/action/__init__.py`) all go through this same mechanism — `plugins/` filenames are prefixed by domain (`api_*`, `bank_*`, `iot_*`, `aprs_*`, `tuxlog_*`, `escm_*`) but nothing in code enforces that grouping.

### UI / portal rendering
`ui/core/portal.py` + `core/jinjaenv.py`/`services/jinjatemplate.py` render Jinja templates from `wwwroot/templates/` and per-solution content under `wwwroot/solutions/<id>/`, selected by `AppInfo.get_current_config('ui','wwwroot')`. `services/outdataformatter.py` (`OutDataFormatter`) renders a `Recordset` through a named view (`$view_name`) for both API responses (`?view=...`) and admin/report pages (e.g. `tools/metadata.py`'s datamodel dump).

### Naming conventions in this codebase
Existing code does not follow PEP 8: no spaces around `=` in assignments/kwargs (`x=1`, `foo(a=1)`), and this style is deliberate/consistent across the whole repo (see the PEP8/naming-convention links left in `README.md` — the author is aware and has chosen otherwise). Match the surrounding style rather than reformatting.
